# Reliability audit — 2026-09-28

## Scope and observed state

This review used `bmad-code-review` on the six GitHub Actions workflows, then traced their release, scan, push, cleanup, and metadata helpers. Baseline: `main` at `b640870df8a9c4fa329539dd60b921372d679611`. The last [Build Release Candidates run](https://github.com/pnetcloud/containers/actions/runs/36406677119) and [Update Metadata run](https://github.com/pnetcloud/containers/actions/runs/36406079535) succeeded on 2026-09-28. GHCR publicly serves the four publishable PostgreSQL 17/18 × Debian Trixie/Bookworm images, and their digests match the four committed `release-metadata/*.json` records. The `18`, `latest`, and `18-pg18.6-ts2.30.1-20260928` tags resolve to `sha256:13f898297d294734306e9e1ad5fb64402e92f912c77240eb4a5874d2e8a65f8a`. There were no Git tags or GitHub Releases. Fifteen older `candidate-*` tags remained visible in GHCR.

The gap reported as “no new images” is therefore a discovery and release-record gap for the latest run, not evidence that its image publish failed. Live deployment of these images into a CloudNativePG cluster was outside this audit.

## Risks needing a bounded proof

- **A12 — older digest retention (unverified, potentially high).** Automatic cleanup collects protected digests from this run's final tags and then calls `cleanup-ghcr-versions.py --delete-untagged`. The script selects untagged versions outside that set. We have not established from GHCR's package-version data whether an older version/date index depends on an untagged platform package version that this could delete. Story 6.7 must inspect real package-version relationships or a faithful fixture before changing deletion policy.
- **A13 — cleanup during an active publish (unverified, potentially medium).** Manual cleanup and `build.yml` have different concurrency groups. The manual job can run while a candidate is assembling; candidate tag age guards reduce risk, but untagged versions may still be selected. Story 6.3 must prove the reachable race before adding coordination.

## Review triage

All three independent review layers completed. A1–A11 are confirmed from the cited code and observed release state. A12–A13 are investigation stories because the registry behavior is not yet proven. The duplicate reports of the dry-run and recent-candidate failure share A5's root cause. No review claim was silently accepted as a production incident; a successful workflow run is evidence of the pipeline outcome only, and the new GitHub Release job has not run on GitHub as of this audit.

## Boundaries and follow-up evidence

The new release path needs a successful `main` workflow run to prove that GitHub permissions, GHCR digest checks, changelog generation, and Release creation work together. Local YAML and generator checks cannot substitute for that live run. GitHub Releases are a source and artifact record; production cluster rollout remains separate.

The follow-up stories are recorded in the `pNet Containers` Multica project as `PNET-48` (push failure), `PNET-49` (SARIF), `PNET-50` (cleanup), `PNET-51` (immutable tags), `PNET-52` (attestations), `PNET-53` (rehearsal), `PNET-54` (retention), and `PNET-55` (GitHub Releases and changelog). `PNET-48` and `PNET-55` have local implementations and await normal review and live workflow proof; the other stories remain open.
